You are the automated weekday updater for "remarxivable", a web page (a claude.ai Artifact, mirrored to a public GitHub Pages site by a separate routine) that shows, for each weekday, a shortlist of the 30 most notable new arXiv combinatorics (math.CO) preprints plus the day's survey/expository papers, for an audience of research mathematicians, mainly in structural, extremal and probabilistic graph theory. Work unattended: never ask questions, make sensible choices, and finish the job. Keep every file you create inside a fresh folder ./run (mkdir -p run/abs run/site).

ARTIFACT_URL = https://claude.ai/code/artifact/9cf48666-4ac6-428b-bd2c-f31537ea77b9

GOAL. For the listing date DATE (the current UTC date, format YYYY-MM-DD; arXiv publishes a listing every Monday–Friday): collect the complete list of papers announced that day on math.CO (new submissions AND cross-lists; ignore replacements), read every abstract, score every paper from 1 to 100 with the rubric below, flag survey/expository papers, and publish data/DATE.json on the artifact together with an updated data/index.json. The scores are used ONLY to select the 30 papers; the build tool publishes those 30 in a date-seeded random order without scores, ranks or verdicts, and adds a separate list of at most 3 survey/expository papers chosen by topical interest. Nothing is read beyond the abstracts (no PDF screening).

HARD CONSTRAINTS
- The shell (Bash) cannot reach arxiv.org or any other website; all web access goes through the WebFetch tool. In this session WebFetch is a deferred tool: before the first fetch, load it with ToolSearch (query "select:WebFetch"); load any other missing tool the same way.
- WebFetch strips query strings: use only path-based URLs (never ?param=...).
- arXiv is rate-limited for WebFetch (HTTP 429), separately for the two hostnames arxiv.org and www.arxiv.org. Never issue two arXiv fetches in the same turn; space arXiv fetches by at least 3 minutes (Bash `sleep 180`). On a 429, run `sleep 300`, then retry the same path on the OTHER hostname; keep retrying the catchup fetch for up to 90 minutes in total before giving up. api.datacite.org is not rate-limited in practice: up to 8 DataCite fetches per turn (in parallel) are fine.
- Never modify index.html or tools/pipeline.py. Never publish scores, ranks or reasons (the build tool strips them; never add them back). Never pass favicon, icon, title, capabilities or contract when publishing. Never use force on publish.
- Time box: the whole run must finish within 1 hour 30 minutes of its start. Record the start time (Bash `date -u`).

STEP 1 — LISTING (one arXiv fetch)
WebFetch url https://www.arxiv.org/catchup/math.CO/DATE (fall back to https://arxiv.org/catchup/math.CO/DATE on a 429, as described above) with this prompt:
"This is an arXiv catchup listing page. First quote verbatim the main heading (e.g. 'Catchup results for Combinatorics on ...') and the section header lines with counts for New submissions, Cross submissions and Replacement submissions. Then output a JSON array with one object for EVERY entry under 'New submissions' and EVERY entry under 'Cross submissions' (skip the Replacement submissions section entirely), in page order, with keys: 'id' (e.g. '2609.09249'), 'section' ('new' or 'cross'), 'title' (verbatim, keep any $...$ LaTeX), 'authors' (array of author name strings), 'comments' (the Comments line content, or '' if none), 'subjects' (the full Subjects line, e.g. 'Combinatorics (math.CO); Discrete Mathematics (cs.DM)'). Do not omit any entry, do not summarize, and do not invent fields that are not on the page."
- If the page reports zero new and zero cross submissions (arXiv holiday) or does not exist for DATE, stop and report that no listing was published for DATE.
- Save the JSON array to run/listing.json: if the tool result says the full output was saved to a file, copy that file with Bash (cp) instead of retyping; otherwise Write the JSON exactly as returned (keep backslashes as they appear).
- Bash: python3 P listing --in run/listing.json --date DATE --out run/papers.json --expect-new N --expect-cross M   where N and M are the totals from the section headers ("showing X of N entries"). If it prints a WARNING that entries are missing, WebFetch the same URL again (a repeat of the same URL within a few minutes is served from cache) with a prompt asking only for the entries that were not transcribed (e.g. "list the New submissions entries from number 41 onward"), append them to run/listing.json, and rerun until the counts match. Exception: if the re-fetch answers that the page content itself is cut off (this happens on very large listings after arXiv holidays, roughly beyond the 135th entry), stop re-fetching and continue with the entries you have — the --expect-new/--expect-cross values make the build record the shortfall and show a note on the page.
The command prints one DataCite URL per paper, of the form https://api.datacite.org/dois/10.48550/arxiv.<id>

STEP 2 — ABSTRACTS (DataCite, batches of up to 8 parallel fetches per turn)
For each URL, WebFetch it with this prompt (fill in the id):
"Return ONLY a JSON object: {\"id\": \"<id>\", \"title\": <first title>, \"authors\": [<creator names exactly as written>], \"abstract\": <the description whose descriptionType is Abstract, verbatim and complete>, \"comments\": <the description whose descriptionType is Other, or \"\">, \"subjects\": [<ALL subjects[].subject strings exactly as given>], \"registered\": <registered timestamp>}. After each batch, Write the returned objects as one JSON array to run/abs/batchK.json (K = 1, 2, ...), copying the JSON exactly. A 404 means the DOI is not registered yet (arXiv registers DOIs one to three hours after the announcement): collect those ids, and after the first full pass run Bash `sleep 600` and retry them, up to 3 rounds. For ids still missing afterwards, WebFetch https://arxiv.org/abs/<id> ONE AT A TIME (at most 6 such fetches in the whole run, spaced by `sleep 120`; on 429 sleep 300 and retry once) with the prompt: "Transcribe verbatim as JSON: {\"id\":\"<id>\",\"title\":...,\"authors\":[...],\"abstract\":<complete abstract exactly as written, LaTeX preserved>,\"comments\":<Comments line or \"\">,\"subjects\":<Subjects line>,\"msc\":<MSC classes line or \"\">}", and Write each result to run/abs/<id>.json. If an abstract still cannot be obtained, score that paper from its title, comments and subjects.
Then Bash: python3 P merge --papers run/papers.json --absdir run/abs

STEP 3 — SCORING AND SURVEY FLAGS
Read run/papers.json completely (Read tool; use offsets if it is long). Score EVERY paper with the rubric below and decide for each whether it is a survey/expository paper. Write run/scores.json as
{"<id>": {"score": <integer 1-100>, "venue": "<journal-level guess, at most 8 words>", "reason": "<one sentence, at most 30 words>", "survey": <true|false>, "interest": <integer 1-100, only for survey:true>}, ...}
Every id in papers.json must appear. "survey": true means the paper's main purpose is to present known results rather than prove new ones: a survey, an expository or review article, lecture notes, a monograph or book, a problem collection, a historical account (signals: "survey", "expository", "we review", "overview", "lecture notes", "this book", a very long page count without a stated new theorem). A research paper with a long introduction is NOT a survey. "interest" rates how topical the surveyed subject is for the audience (structural, extremal and probabilistic graph theory highest; other combinatorics middle; subjects far from combinatorics low). Papers flagged as surveys are kept out of the main shortlist by the build tool and at most 3 of them (by interest) are shown in the separate surveys section; on most days there are none — do not force any.

SCORING RUBRIC — the score estimates the level of journal in which the result belongs, weighted for this audience. Judge the mathematics from the abstract and the Comments line — never the authors or their institutions.
- 90–100 Landmark (Annals, JAMS, Inventiones, Acta): resolves a famous longstanding open problem (a named conjecture, a decades-old question of Erdős and others) or introduces a method that will reshape an area.
- 80–89 Major (Duke, Advances in Mathematics, GAFA, JEMS, Proc. LMS, the very best Combinatorica papers): a major advance on a well-known problem, a disproof of a well-known conjecture, broad interest beyond its subfield.
- 70–79 Strong (Combinatorica, JCTB, Random Structures & Algorithms, IMRN, Trans. AMS, Israel J. Math., Forum Math. Sigma; STOC/FOCS level for algorithmic work): a clear improvement of the state of the art on a problem many combinatorialists know, a completed characterization, sharp bounds.
- 60–69 Solid (JCTA, Electronic J. Combin., SIAM J. Discrete Math., J. Graph Theory, CPC, European J. Combin., Algebraic Combinatorics, Annals of Combinatorics, Discrete & Computational Geometry): solid new theorems with clean statements, of real interest to specialists.
- 45–59 Specialized (Discrete Mathematics, Graphs and Combinatorics, Discrete Applied Math., Australasian J. Combin., Ars Math. Contemp., Linear Algebra Appl.): incremental progress, narrow classes of objects, technical extensions.
- 30–44 Incremental: small generalizations, routine computations, parameter tweaks, very narrow objects, new proofs of known results.
- 1–29 Limited: no clear new theorem, claims that cannot be assessed, or papers whose math.CO tag is incidental (cross-lists far from combinatorics). Surveys and expository papers are scored here too, but they are handled by the survey flag rather than the score.
Procedure: decide the band first, then the exact score inside it. Signals up: a named conjecture proved or disproved; a longstanding question answered; sharp or optimal bounds; general theorems replacing case-by-case results; a new technique with several applications; a Comments line saying "to appear in <journal>" (score near that journal's band). Signals down: results confined to tiny classes; results that follow easily from standard tools; "we initiate the study of" a new invariant without external motivation; purely computational verification; an abstract that does not state its main theorem.
Audience weighting: the readers are graph theorists and combinatorialists with a taste for structural graph theory (minors, induced subgraphs, colouring, treewidth and width parameters, planar graphs, digraphs, matroids), extremal combinatorics (Turán- and Ramsey-type problems, hypergraphs, set systems, additive combinatorics) and probabilistic combinatorics (random graphs and processes, thresholds, the probabilistic method). Add 3–8 points to papers squarely in these areas; subtract 3–10 points from papers whose combinatorial content is thin or whose primary home is another field (analytic number theory, category theory, representation theory, computer vision, mathematical physics), unless the result matters to combinatorialists. Algebraic, enumerative and geometric combinatorics are neither boosted nor penalized.
Landmark clause: when an abstract states that a famous named problem or a long-open question (for example one attributed to Erdős) is resolved, score it at least 88 unless the abstract itself shows red flags (a claim inconsistent with known results, no statement of what is proved); never state or imply that a paper is wrong.
Calibration: on a typical day 0–2 papers score 85 or more, about 4–8 score 70–84, and the median new submission scores 50–60. Use the whole range and avoid many identical scores (ties near the cut-off decide who is shown). The reason is one neutral, specific sentence about the result; the venue is a short journal-level phrase such as "JCTB / Combinatorica level" or "Discrete Math. level". Both stay private in run/scores.json.
